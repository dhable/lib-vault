# lib-vault — Design Decisions

Companion to [`design.md`](design.md). Section references (§) point there.
The `lib-vault` crate (`lib-vault/src/`, API sketch v10) is the source of truth; where this log and the sketch disagree,
the sketch wins and this log is out of date.

## Decisions made

### Core API (sketch v10)
| # | Topic | Decision | Ref |
|---|---|---|---|
| D31 | Pluggable storage | Object data lives behind a `Store` trait: `list`, `delete`, `open_read`, `open_write`. The filesystem is the first backend; databases, object stores and in-memory stores are also intended. The vault no longer *is* a directory. | §2, §5 |
| D32 | Pluggable claiming | Exclusion is a separate `Claimer` trait. `try_lock(key)` (renamed from `try_claim` in v6) returns only a lock (`Box<dyn ClaimLock>`); the `Vault` builds the `Claim` from store + key + lock, so claimers outside the crate can be written and never see the store. `Vault::new(store, claimer)`. Resolves P28; supersedes D25, D30. | §2, §6 |
| D33 | Async-first, runtime-agnostic | `lib-vault` has no runtime dependency and exposes only `futures` traits and types, so a `lib-vault-xxx` backend can target any async runtime. Each backend chooses its runtime and documents it: `lib-vault-memory` needs none, `lib-vault-posix` requires the app to run on tokio (D56). **Async trait methods** (`Store::*`, `Claimer::try_lock`) return the driver's future type (`D::Fut`, D58) or `BoxFuture` (the traits must be usable as `dyn`). **Async inherent methods** (`Vault::claim`, `Vault::shutdown`, `Claim::list`/`delete`/`open_read`/`open_write`) are `async fn`, which also makes their checks run when polled rather than when called. Release is synchronous (D39). Which runtimes fit the remaining `Send` bounds: P50. Supersedes D3 and the v2 async plan. | §2, §7, §11 |
| D34 | `Key` type | Object names are `Key`, an `Arc<str>` newtype in unix path syntax (`a/b/c`), not `Path`. **Strict canonical form**: not empty, no leading/trailing `/`, no `//`, no `.`/`..`, no NUL, plus the name policy and caps (D6). One string has exactly one valid spelling. There is no root key (D48). Cheap to clone. | §3 |
| D35 | `Key::join` | Always nests: unlike `Path::join`, the argument can never replace the base. This is what makes scoping a confinement mechanism. Returns `Result<Key, KeyError>`: it fails only with `TooDeep`/`TooLong` when the joined key exceeds the caps (D6), so every `Key`, including a claim's resolved full keys, obeys them. The `Claim` methods propagate it as `Error::Key`. | §3, §4.1 |
| D6 | Name policy | Applies to **every key and every backend**, enforced by `Key::validate`. Each component uses only `[A-Za-z0-9._ -]`, doesn't start with `-`/space or end with `.`/space, isn't a Windows device name (`CON`, `PRN`, `AUX`, `NUL`, `COM0`–`9`, `LPT0`–`9`, with any extension, any case) and doesn't start with `.vault` (any case). Caps: component ≤ `MAX_COMPONENT_LEN` = 255 bytes, ≤ `MAX_DEPTH` = 32 components, ≤ `MAX_KEY_LEN` = 1024 bytes. New `KeyError` variants: `InvalidChar`, `BadComponentStart`, `BadComponentEnd`, `Reserved`, `ComponentTooLong`, `TooDeep`, `TooLong`. The case-collision rule needs stored state, so it's a `Store` contract requirement for every backend (`open_write` must fail when the key differs from an existing one only by ASCII case). Resolves P38. | §3, §5, §10 |
| D36 | Scoping | A `Claim` keeps its claimed key (`base`) and the unscoped store pointer (`D::StorePtr`, D74); each method resolves its argument with a private `resolve_key(base, key)` (`None` → `base`, `Some(k)` → `base.join(k)`) and calls the store with the full key. Every key a claim receives is relative to the claimed key and can't leave it. The separate `ScopedStore` type was removed (replaced by that function call). Resolves P27. | §4.1 |
| D37 | Claim thread model | Exclusive use comes from every `Claim` operation taking **`&mut self`**; `Claim` never implements `Clone`, and nothing relies on `Claim` being `!Sync` (a `&Claim` can do nothing). **`Send` depends on the I/O driver (D58, D74):** in `AsyncIoDriver`, `Claim<AsyncIoDriver>` and `Vault<AsyncIoDriver>` are `Send` (and `Vault` is `Send + Sync + Clone`), inferred rather than declared (no `unsafe impl`, no `negative-impl` dependency), and `&mut Claim` is `Send`, so tasks using a claim stay spawnable on work-stealing runtimes. In `OwnedBufDriver` they hold the store in an `Rc` and are deliberately `!Send`: one vault per thread, as thread-per-core runtimes expect; exclusion across threads still comes from the claimer. Supersedes D27; resolves P18, P32, P33. | §4.2 |
| D38 | Claim operations | `list`, `delete`, `open_read` (→ `D::Reader<'a>`), `open_write` (→ `D::Writer<'a>`) on keys within the claim. Separate read and write handles, because random-access read/write/seek doesn't map onto object stores. The handle types depend on the I/O driver (D58). Resolves P30. Replaces `sub_claim`, `open`/`open_dir`, `Dir`, `StoreObject` (D7, D9, D10, D21, D22). | §4.3, §5 |
| D39 | `ClaimLock` release | A claimer's lock has one method, `release(self: Box<Self>) -> Result<()>`: **synchronous and non-blocking**. Each implementation handles its own async work (its own thread or runtime); the library never runs a future in `release` or `Drop`. **`Ok` means the lock is released**, so the same key can be claimed again immediately. Called from `Claim::release` or `Claim::drop`. Supersedes the v6–v8 async `release` run with `block_on` in `Drop`. Resolves P44, P46, P47. | §4.4, §6 |
| D40 | `list` result | `Vec<Key>`, relative to the listed key; "prefix" means component prefix. `claim.list(None)` lists everything in the claim (D48). Resolves P31. | §5 |
| D11 | Giving up a claim | `Claim::release(self) -> Result<()>` consumes the claim, releases the lock and returns any error. Dropping a claim releases the lock if `release` wasn't called and logs errors with `tracing`. Both go through a private `release_lock`; the lock is an `Option<Box<dyn ClaimLock>>` that is `take()`n, so it's released at most once, and a lock-less claim (failed or cancelled `try_lock`, D47) skips it. Because `release` consumes the claim, no claim outlives its lock, and the outstanding count drops as soon as `release` returns. A failed release can't be retried. Resolves P48, P49. | §4.4 |
| D41 | Shutdown state | One `Arc<Mutex<VaultState { shutting_down, outstanding_claims, waiters: Vec<Waker> }>>` shared by every `Vault` clone and every `Claim` replaces the `AtomicBool` gate, so the flag and the count can't be observed out of step. `claim` checks the flag and counts up under the mutex, then drops the guard **before** awaiting `try_lock` (so its future is `Send` and can't block other threads on the mutex); counting up first makes shutdown wait for in-flight claims. `Claim::drop` releases the lock if still held, counts down, and wakes the waiters, after unlocking, when the count reaches zero. `shutdown` sets the flag and awaits a `poll_fn` that is `Ready` at zero and otherwise registers its waker (deduplicated with `will_wake`). Resolves P35, P42, P43. | §4.5 |
| D47 | In-flight claim accounting | `Vault::claim` builds the `Claim` (lock-less) under the mutex right after counting up, awaits `try_lock`, then `set_lock`s it. If `try_lock` fails or the `claim` future is dropped, the lock-less `Claim` is dropped and its `Drop` counts down, so refused and cancelled claims never leak a count. Resolves P45. | §4.5 |
| D48 | No root key | The empty string is not a valid `Key` (`KeyError::Empty`); `Key::root`/`is_root` are gone, so the whole vault can't be claimed. A claim refers to its own key with `None`: `Claim::list`, `delete`, `open_read` and `open_write` take `key: impl AsKeyRef`, implemented for `&str` (validated with `Key::new`; invalid → `Error::Key`), `&Key` and `Option<&Key>`, where `None` means the claimed key itself. No impl for owned `Key` (pass `&key`), and a single `Option` impl so a bare `None` infers. `Store` still takes `&Key`, so backends always receive a full, non-empty key; `Claim` resolves `None`/`Some` itself (D36). Consequences: `join` always nests (`a` + `b` = `a/b`); `strip_prefix` of a key by itself is `None`; `parent` of a single-component key is `None`. Resolves P6. | §3, §4.1 |
| D49 | Workspace layout | A Cargo workspace: `lib-vault` (the core API, all existing code), `lib-vault-posix` (the filesystem backend, D16–D19, D24, D29) and `lib-vault-memory` (the in-memory backend and test double). Backends are separate crates so the core doesn't pull in platform or syscall dependencies. Both backend crates are empty for now. | §12 |
| D50 | Shared dependencies and metadata | Package `version` and `edition` are declared once in `[workspace.package]` and inherited with `version.workspace = true` / `edition.workspace = true`, so the crates are versioned and built together. Third-party dependencies are declared once, in the root `Cargo.toml` under `[workspace.dependencies]` (version, `default-features` and features), and member crates opt in with `<name>.workspace = true`. Every crate then uses the same version and feature set, and an upgrade is a one-line change. A member may add features on top (`features = [...]`) but can't turn the workspace's default features back off, so defaults are decided at the workspace level. | §12 |
| D51 | In-memory backend | `lib-vault-memory` provides `MemoryStore` (implementing `Store<AsyncIoDriver>`), `MemoryClaimer` and `vault()` (a `Vault<AsyncIoDriver>`) for tests and getting started; not for production. Store: objects in a shared `BTreeMap` (clones share it); reads are snapshots; writes are buffered and **committed on `close()`** (a writer dropped without `close()` is discarded); case collisions fail with `MemoryError::CaseCollision` at `open_write` and again at commit; an object at `a` may coexist with `a/b`. Claimer: a shared set of held keys (clones share it), so exclusion covers `Vault`s sharing a claimer but not separate claimers or other processes; works with any store. Its integration tests (`lib-vault-memory/tests/`) cover the core API's documented behavior: scoping, object semantics, the name policy and caps, claim conflicts, release and shutdown. | §12 |
| D58 | I/O drivers | The object-handle style is a type parameter, not a Cargo feature (mutually exclusive features conflict when Cargo unifies them across a dependency graph). `lib_vault::io_driver` defines an `IoDriver` trait (`Sized + 'static`; originally sealed, unsealed by D77) with associated `Reader<'a>`, `Writer<'a>`, `Fut<'a, T>` and `StorePtr` types (D74), and two byte drivers. **`AsyncIoDriver`** (work-stealing runtimes such as tokio, async-std, smol): `BoxFuture`, borrowed buffers through `Pin<Box<dyn AsyncRead/AsyncWrite + Send>>`. **`OwnedBufDriver`** (thread-per-core, completion-based runtimes such as monoio, tokio-uring): `LocalBoxFuture`, owned buffers through a `LocalBoxStream` of `Bytes` chunks to read and a `Box<dyn ObjectWrite>` to write (`write(Bytes)` and `close()` returning `LocalBoxFuture`), none of them `Send`. `Store<D>`, `Vault<D>` and `Claim<D>` are generic over the driver; `dyn Store<D>` stays dyn-compatible because the driver is a trait parameter, with the generic associated types on `IoDriver` rather than on `Store`. `Claimer`/`ClaimLock` aren't driver-specific (P50). Backends implement `Store<D>` for the drivers they support. `Vault<D>` implements `Clone` by hand (deriving would require `D: Clone`). Supersedes the single `ObjectReader`/`ObjectWriter` pair of D38. | §4.3, §5, §7 |
| D42 | Handle lifetimes | `open_read`/`open_write` take `&'a mut self` and return handles borrowing `'a`, so a claim can't be released or dropped while a handle is alive (compile error E0505), and a claim has at most one open handle at a time, with no `list`/`delete` meanwhile. Accepted. Resolves P29. | §4.3 |
| D43 | Object semantics | `delete` of a missing key succeeds (like HTTP `DELETE`); `open_read` of a missing key is an error; `open_write` creates or overwrites. When written data is committed/flushed, and what happens to in-flight writes after release, is documented by each `Store`. `list` has no paging or limits in the first revision. | §5 |
| D44 | Claim conflicts | Documented on `Claimer`: a claim covers its key and everything beneath it (component-wise, `Key::starts_with`); conflicts go both ways (descendants *and* ancestors); disjoint keys don't conflict; exclusion holds across tasks, `Vault`s and processes. `try_lock` **never waits**: one attempt, an error on conflict; callers retry with their own backoff/timeout. Dropping the future releases anything partially acquired. Resolves P36, P40; makes P19 moot. | §6 |
| D45 | Store/Claimer pairing | Not checked by `Vault::new`. Each claimer documents which stores it works with (e.g. `FsClaimer` only with `FsStore`). Pairing is one-directional: stores work with any claimer (D75). Resolves P37. | §6 |
| D46 | What shutdown waits for | Outstanding claims only, not other `Vault` clones. Several clones may await `shutdown` at once. A task that holds a claim and awaits `shutdown` never finishes (document it). Resolves P2. | §4.5 |
| D12 | Error type | A `thiserror` enum, `#[non_exhaustive]` so variants can be added without a breaking change. `ShuttingDown`: `Vault::claim` after `shutdown` started. `Key(KeyError)`: an invalid key (`From<KeyError>`, so `?` works on `Key::new`). `AlreadyClaimed { key }`: `try_lock` refused because of a conflicting claim (D44). `NotFound { key }`: no object at the key (e.g. `open_read`, D43). `ClaimError` / `StoreError`: any other claimer or store failure, wrapping a `Box<dyn Error + Send + Sync>` source so third-party implementations can pass their own errors through. Chosen over snafu: other crates construct these errors, and thiserror adds no types to the public API. Resolves P4. | §7 |
| D13 | Shutdown semantics | Stop issuing new claims, then wait until all outstanding claims are dropped (and therefore released, D39). `async fn shutdown(self)`. | §4.5 |
| D26 | Diagnostics | Use the `tracing` crate for debug info and non-fatal warnings. No warning structs are returned from the API. | §12 |
| D2 | Claim modes | Exclusive claims only. No shared/read claims. | §6 |
| D20 | Compile-time scoping | Treated as protection against harness bugs, not a security boundary. Security lives in key validation and backend resolution. | §1 |
| D8 | Quotas | Not enforced in-library; deferred to the backend / OS. | §9 |
| D4 | Deployment model | In-process library only. No process-wide self-sandboxing. | §9 |
| D5 | Multiple applications | Apps may run as different uids/gids, with no shared config or agreement beyond "same backend + lib-vault". | §6 |
| D76 | Tests as usage examples | Integration tests double as examples of the public API, so **tests call the API directly**: no shared `tests/common` module and no helpers that wrap API calls (building a vault, claiming, writing, reading, listing, downcasting a backend error). A test builds its vault with `Vault::new(store, claimer)`, claims with `v.claim(Key::new(..).unwrap())`, writes with `open_write` → `write_all` → `close()` → `drop(w)`, and reads with `open_read` → `read_to_end` → `drop(r)` (the explicit drops are required by D42). The verbosity is accepted: it shows what callers write. **Helpers are fine** for test machinery that isn't API usage: filesystem inspection (`tree`), thread and timing plumbing (`spawn_shutdown`), or one assertion repeated within a single file (`refused`, `unsupported`). Such helpers stay file-local, even if that means duplicating one in two files. | §12 |
| D77 | I/O drivers | Prepares for structured stores (e.g. SQLite with a SeaORM-style mapping, where `open_read` leads to an app's own `MyDataObj` rather than bytes). The I/O mode becomes an **I/O driver** that backends can define: module `rt` → `io_driver`, `IoMode` → `IoDriver`, `SharedMode` → `AsyncIoDriver`, `OwnedMode` → `OwnedBufDriver` (named for their data shape, `AsyncRead`/`AsyncWrite` streams and owned `Bytes` chunks, not the runtime), generic parameter `M` → `D`. **Unsealed:** any crate may implement `IoDriver`. The two byte drivers stay in `lib-vault` as the shared contract between byte backends and apps (so app code and the memory test double work against any byte backend); a structured driver lives with its backend, and its handles carry the typed API (e.g. `reader.get::<T>()`), which `Claim` passes through untouched. **`IntoStorePtr<S>` is implemented by the driver** (`impl<S: Store<MyDriver>> IntoStorePtr<S> for MyDriver`) and `Vault::new<S>(store: S, claimer)` requires `D: IntoStorePtr<S>`: the old form, `impl<S> IntoStorePtr<MyDriver> for S`, can't be written outside `lib-vault` (orphan rule, E0210). `Claimer`/`ClaimLock` are unaffected. Refines D58, D74. | §4.3, §5, §7 |

### Filesystem backend (`FsStore` + `FsClaimer`)
These were core decisions when the vault was filesystem-only. They now describe the first backend.

| # | Topic | Decision | Ref |
|---|---|---|---|
| D1 | Syscalls | The core API uses only std and `futures` types. The fs backend may use a syscall crate for `openat2`/`openat`/`fstatat`/`unlinkat`/`renameat`, with its own resolver so link, type and name policies stay ours. | §8.1 |
| D16 | Cross-process lock mechanism | `flock` on per-key **lock files** beside the objects ("lock-file v1", D67): shared locks on each ancestor component's lock file, an exclusive lock on the target's lock file, top-down, with verify-after-lock. No shared lock-file *directory* and no shared writable metadata. (Originally "inode-lock v1", locking the objects' own inodes; changed by D67 before implementation.) | §8.3 |
| D17 | Links and special files | Symlinks, multiply-linked regular files, mount crossings, FIFOs/sockets/devices are all refused, with checks done on handles, not paths. | §8.2 |
| D18 | Non-blocking acquisition | Each `try_lock` is one pass of `try_lock_shared`/`try_lock`; on `WouldBlock` it releases what it took and fails. Never blocks in `flock(2)`. Waiting is the caller's retry loop (D44). | §8.3 |
| D19 | Claimed files | Write **in place**: the object's inode never changes, so the claim's `flock` (D59) stays on the right file. Crash safety comes from the optional journal (D63). (D60's temp file + rename was superseded.) | §8.3 |
| D23 | Timeouts | No built-in claim timeout or wait. Callers that retry `claim()` bound the loop with their own timeout. | §6 |
| D24 | Platforms | **Linux and macOS** first; BSD and Windows later. Linux ≥ 5.6 uses `openat2` for resolution (D53); macOS 15+ resolves per component with `openat(O_NOFOLLOW)` plus `O_NOFOLLOW_ANY` for leaf opens (D54). | §8.1 |
| D28 | Above-root ancestor locks | ~~Shared locks on every directory above the vault root, up to `/`, per claim, to detect nested vault roots.~~ Superseded by D72: nested roots aren't allowed, so these locks were removed. | §8.3 |
| D29 | What release does (fs) | Release every lock (target, then ancestors bottom-up), close fds, update the in-process registry. **No implicit `sync_all`.** For `flock` this is just closing fds: synchronous, non-blocking, and done when `release` returns. | §4.4 |
| D52 | Syscall crate | `rustix` for `openat2`/`openat`/`fstatat`/`unlinkat`/`renameat`/`statfs`: safe wrappers over the raw calls with no libc-level `unsafe` in our code, at the cost of one dependency. Resolves P12. | §8.1 |
| D53 | Minimum Linux kernel | **5.6**, so `openat2` (with `RESOLVE_BENEATH`/`RESOLVE_NO_SYMLINKS`/`RESOLVE_NO_MAGICLINKS`/`RESOLVE_NO_XDEV`) is always available for resolution; there is no per-component `openat` fallback for resolution on Linux. (Locking still walks per component, §8.3.) Resolves P13. | §8.1 |
| D54 | Minimum macOS | **macOS 15 (Darwin 24)**, the oldest release Apple still supports as of October 2026. No runtime version check: the backend targets the APIs available in macOS 15 and documents the minimum. `O_NOFOLLOW_ANY` (macOS 11+) is therefore always available. Resolves P25. | §8.1 |
| D55 | MSRV | **Rust 1.89**, the first release with `File::lock`/`try_lock`/`lock_shared` (used for `flock`, §8.3). Resolves P14. | §8.3 |
| D56 | Runtime for the fs backend | `lib-vault-posix` depends on **tokio** and **requires the app to run on a tokio runtime**: it uses the ambient runtime (e.g. `spawn_blocking` for its blocking syscalls) and doesn't own one. This is the app's choice when it picks the posix backend, and the crate documents it prominently; its futures panic if polled outside a tokio runtime. tokio is not a dependency of `lib-vault` or `lib-vault-memory` (Cargo dependencies are per crate), so apps using another backend can use any runtime. `ClaimLock::release` is synchronous (D39) and must not need the runtime, since it may run from `Drop` on any thread. Resolves P39. | §8.1, §11 |
| D57 | Performance harness | `criterion` benchmarks in `lib-vault-posix/benches/` measuring the lock-file protocol (per-claim fd and syscall counts, acquisition latency vs depth and contention). Resolves P26. | §12, §13 |
| D59 | File-level claims | Allowed. A claim's exclusive lock is on **that key's own lock file** only (D67), not its parent directory, so sibling objects can be claimed independently. Ancestors get shared locks top-down (D16), so a claim on a parent directory still conflicts. Resolves P8. | §8.3 |
| D60 | Atomic writes | ~~Write a temp file and `renameat` it over the key, moving the claim's lock to the new inode before the rename.~~ Superseded by D63: keeping the inode stable avoids the lock hand-off, and journaling gives the crash safety. | §8.3 |
| D61 | Read-only access | No read-only fallback for claims. If the process can't open the claimed object read-write (e.g. a different uid with read-only permission), the claim **fails with a permission error** (`Error::ClaimError` / `StoreError` wrapping an `io::Error` of kind `PermissionDenied`). `AlreadyClaimed` stays reserved for conflicts with other claims, so a caller retrying on `AlreadyClaimed` never retries a claim that can't succeed. Exclusion is unaffected either way: one claim per object (D2). Resolves P24. | §8.3 |
| D62 | POSIX ACLs | Not supported on vault-managed objects. The backend never reads or writes ACLs; cross-uid sharing is only through group mode (`2770`/`0660`, §9). Objects are created with explicit modes (`fchmod`). Default ACLs on the root or its directories would still be inherited by new objects and could widen access beyond the mode: a root with extended ACLs is refused (D70). Resolves P10. | §9 |
| D63 | Write journaling (fs backend) | Optional, **on by default**, chosen when the store is created: `FsStore` takes construction options, e.g. `FsStoreOptions { journaling: bool, .. }` (the same place the sharing mode is chosen, §9; D25's "no `VaultOptions`" is about `Vault`, not backend constructors). **Journal file:** `.vault-journal-<name>` beside the object (reserved `.vault` prefix, D6: can't collide with a key, never listed), with a header holding a magic number, the content length and a checksum, and a completion marker. **With journaling:** `open_write` creates the journal; `write` appends only to the journal (the object is untouched); `close()` completes the header, fsyncs the journal and directory (`F_FULLFSYNC` on macOS), then truncates and rewrites the object **in place**, fsyncs it, unlinks the journal and fsyncs the directory. A writer dropped without `close()` never touched the object, so its journal is deleted (best effort). The commit point (D43) is `close()`, durable once it returns. Costs about 2× the bytes written. **Without journaling:** truncate, write in place, fsync; a crash can leave a partial object. **Leftover journal:** in either mode, `open_read`/`open_write` on a key whose journal exists fail with `Error::StoreError` wrapping a posix error such as `InterruptedWrite { key, journal }` that names the file. Only that object is affected; `list` and `delete` work normally (`delete` doesn't remove the journal). Checked at open time; no scan when the store is created. **Recovery is manual:** a complete journal (valid checksum) holds the full new content and can be copied over the object; an incomplete one can be deleted. The library offers no replay API. Supersedes D60; resolves P21. | §8.3, §10 |
| D64 | Strict modes (fs backend) | An `FsStoreOptions` option, `strict_modes: bool`, **on by default** (like sshd's `StrictModes yes`). **When enabled**, `FsStore` construction mimics sshd's `StrictModes` check: it walks from the vault root up to `/`, opening each directory without following symlinks and `fstat`ing the handle. Each ancestor must be owned by root or the effective uid and not writable by group or others, unless it is root-owned with the sticky bit set (like `/tmp`, where others can't rename or delete our entries). The root itself must match its sharing mode (private `0700`, or group mode's setgid `2770` for the vault group, §9). Any violation fails construction with an error naming the offending directory and the reason. **When disabled**, none of these ancestor checks run. **Why:** a directory above the root that someone else can write lets them swap the path for one they control before the store opens it; after that the backend works from the held root handle (§8.1), so the check protects the moment of opening. Resolves P22. | §9 |
| D65 | Case-collision races | The case rule (D6) is checked when an object is created, under the claim that creates it. Within one claim, creates are sequential (one open handle at a time, D42), so the check is race-free. **To create objects whose names might collide by case, claim their parent directory** and create them under that claim. Claims on sibling keys (`a/Foo` and `a/foo`) are disjoint (D44) and hold only a shared lock on the parent, so two of them creating at the same time can both pass the check: this is a documented residual race, not prevented by the library. On a case-insensitive volume (default APFS, case-folded ext4 directories) the second create would land on the first object. Resolves P20. | §5, §8.3 |
| D66 | `FsStore` options and verify retries | `FsStore::new(root, options: FsStoreOptions) -> Result<FsStore, PosixError>`. `FsStoreOptions` has private fields and builder methods (`sharing`, `journaling`, `strict_modes`, `max_verify_retries`) on top of `Default`, so options can be added later without breaking callers (public fields would break exhaustive struct literals, and `#[non_exhaustive]` would forbid construction outside the crate). Defaults: `Sharing::Private`, journaling on (D63), strict modes on (D64), **`max_verify_retries = 3`**. **Verify retries:** per lock level, within one `try_lock` call (so `try_lock` still never waits on another claim, D44): when verify-after-lock finds the name now points at a different inode (§8.3 step 3), that level is unlocked, reopened and relocked, up to the limit; `0` fails on the first mismatch. **Exhausted:** the claim fails with `Error::ClaimError` wrapping `PosixError::VerifyRetriesExhausted { key, path, attempts }`, not `AlreadyClaimed`, because it isn't a conflict with another claim but a path that something outside the vault keeps changing. Resolves P23. | §8.3, §9 |
| D67 | Lock files and create-on-write | Each key component is represented by a hidden lock file `.vault-lock-<name>` in its parent directory (reserved `.vault` prefix, D6: never a key, never listed). To claim `c1/…/cn`: shared locks on `.vault-lock-c1` … `.vault-lock-c(n-1)`, then an exclusive lock on `.vault-lock-cn`, top-down, each verified after locking (same name → same inode, `nlink > 0`; retries per D66). A claim on `a` and one on `a/b` meet on `.vault-lock-a` (exclusive vs shared), so D44's ancestor and descendant conflicts hold; siblings use different lock files. **Objects are created on write, never on claim**: claiming and releasing a missing key leaves no object. Intermediate **directories** are created on claim, because a lock file needs its parent directory; they aren't objects and don't appear in `list`. **Lock-file lifetime:** an exclusive claim unlinks its own lock file on release while still holding it; a process that opened it just before fails verify-after-lock (`nlink == 0`) and retries with a new file. Lock files used only as shared ancestor locks may remain (empty, hidden, reused), and a crash can leave stale ones; an unlocked lock file is simply reused. On case-insensitive volumes `.vault-lock-Notes` and `.vault-lock-notes` are one file, so they still exclude each other. Since the claim no longer opens the object, D61's permission failure surfaces at `open_write` (or at claim time if the lock file can't be created). Resolves P1; changes D16 and D59. | §8.3 |
| D68 | Optional hardening | Deferred to v2: a dangerous-name denylist, HMAC tamper detection and an audit log are not in v1. Resolves P11. | §10 |
| D69 | Network filesystems | At `FsStore` construction, `statfs` detects a non-local filesystem (Linux `f_type` magic numbers; macOS `MNT_LOCAL` not set). The store logs a `tracing` warning and continues: `flock` over NFS/SMB may not exclude processes on other hosts. Resolves P16. | §8.3, §9 |
| D70 | Extended ACLs on the root | `FsStore` construction fails with `PosixError::ExtendedAcl { path }` if the vault root has extended ACLs (Linux: `system.posix_acl_access`/`system.posix_acl_default` xattrs; macOS: an ACL on the root, via `acl_get_fd_np`). Always checked, independent of `strict_modes`, because ACLs are unsupported (D62) and an inherited default ACL could grant access beyond the object modes. Resolves P63. | §9 |
| D71 | Unreadable ancestors | ~~Every directory from the vault root up to `/` must be readable, so the D28 locks can be taken.~~ Superseded by D72 along with D28. | §8.3 |
| D72 | Nested vault roots | **Not allowed:** a vault root must not be inside another vault's tree, and a vault's tree must not contain another vault root. Documented, not detected at runtime: without shared metadata there's no reliable way to recognize another vault, and with lock files (D67) the outer and inner vaults would lock different files for the same directory. If two vaults do nest, exclusion between them isn't guaranteed. Consequently the per-claim shared locks above the root (D28) and the readable-ancestors requirement (D71) are removed, saving fds and syscalls on every claim. Strict modes (D64) still checks the ancestors, using `fstatat`, which needs only search permission. Resolves P64; supersedes D28, D71. | §8.3, §9 |
| D73 | Filesystem backend implementation | `lib-vault-posix` implements `Store<AsyncIoDriver>` (`FsStore`) and its paired `FsClaimer`, with `FsStoreOptions`/`Sharing`/`PosixError` (the original `vault(root, options)` helper was removed by D75), per D16–D19, D52–D56, D59–D72. Implementation notes, beyond or departing from earlier decisions: **(1)** paths are resolved **per component** with `openat(O_NOFOLLOW)` and an `fstat` check (type, single link, same device) on both Linux and macOS; `openat2` isn't used, because the lock-file walk (D67) visits every component anyway. D53's Linux 5.6 minimum is kept but no longer technically required. **(2)** macOS ACL detection (D70) calls `acl_get_fd_np`/`acl_get_entry`/`acl_free` through a small `unsafe extern` block, since ACLs aren't visible as extended attributes there and neither `rustix` nor `libc` binds them: an exception to D52's "no libc-level `unsafe`". **(3)** Lock and journal names longer than the 255-byte file-name limit (a key component may be 255 bytes on its own) become `.vault-lock-#<hash>` / `.vault-journal-#<hash>`, hashing the ASCII-lowercased name, so case-aliased names still share a file and a hash collision can only over-exclude. **(4)** `open_write` checks an existing object up front (symlink, special file, hard link, directory), even though journaling defers touching it until `close()`. **(5)** If a journaled commit fails after it started, the journal is kept (it's the only complete copy) and the next open reports `InterruptedWrite`. Tested on macOS 26 (39 tests, including a cross-process `flock` test); not yet run on Linux. | §8, §9, §12 |
| D74 | Store pointer per driver | `Store<D>` has no `Send`/`Sync` supertraits (only `'static`), so an `OwnedBufDriver` store can hold `!Send` runtime state (an `Rc`, a ring handle). The bounds move to the driver's `IoDriver::StorePtr`, how a `Vault` and its claims hold the store: `Arc<dyn Store<AsyncIoDriver> + Send + Sync>` in `AsyncIoDriver`, `Rc<dyn Store<OwnedBufDriver>>` in `OwnedBufDriver`. `StorePtr: Clone + Deref<Target: Store<Self>>`, so `Claim` calls the store the same way with every driver. `Vault::new<S>(store: S, claimer) where D: IntoStorePtr<S>`: each driver implements `IntoStorePtr<S>` for every store meeting its bounds (the driver is the implementing type, D77) (`Send + Sync` stores in `AsyncIoDriver`, any store in `OwnedBufDriver`), so existing backends' stores are accepted unchanged. Consequence: `Claim<OwnedBufDriver>` and `Vault<OwnedBufDriver>` are `!Send` (D37). Resolves the store half of P50. | §2, §5, §7 |
| D75 | Choosing a claimer for `FsStore` | The posix API makes the claimer a visible, separate choice, because `FsStore` with a non-`flock` claimer (e.g. a future ZooKeeper-based `ZkClaimer` for hosts sharing storage) is an expected common case. **(1)** No `lib_vault_posix::vault()` helper: a vault is always `Vault::new(store, claimer)`. **(2)** The constructor is on the claimer, `FsClaimer::new(&FsStore)` (was `FsStore::claimer()`), so the dependency points the way it really runs: `FsClaimer` needs an `FsStore` tree for its lock files, while `FsStore` never relies on the claimer (it creates its own directories; lock files exist only with `FsClaimer`). **(3)** Documented in the crate docs and README with a claimer table, plus the rule that **every process using a root must use the same kind of claimer** (different claimers don't see each other's claims); documented, not detected, like D72. **(4)** `tests/claimers.rs` runs `FsStore` with a `MemoryClaimer` to guard the independence. `lib_vault_memory::vault()` stays as a test shortcut. Refines D45, D73. | §6, §8 |
